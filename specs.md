# CropTrail

> Application specification generated by the Application Specification Builder. Treat this document as the source of truth for planning and implementation.

## Instructions for the implementation team or AI coding assistant

## 1. Project name and overview

### Project name

CropTrail

### Overview

CropTrail is a mobile-first web app (a web client talking to a server over a JSON HTTP API) that acts as a "farm memory with a brain" for small farmers. It has four layers: a **ledger** that turns quick text, voice or photo logs into structured farm records; a **climate intelligence layer** that combines weather forecasts, observed weather history and Sentinel-2 satellite crop-health (NDVI) for each plot; a **bounded agent** that answers questions only by calling ledger, weather, satellite and price tools; and an **evidence engine** that detects severe weather over a farmer's plots, opens a suspected loss event, and assembles a claim-ready PDF evidence pack.

Primary journey: farmer logs activities through the season → CropTrail keeps a per-plot ledger and risk score → severe weather is observed over a plot → the app alerts the farmer, starts a 72-hour reporting countdown, and generates an evidence pack combining the farmer's records, photos, weather data and satellite change.

Scope: a 48-hour hackathon MVP for a live demo with one seeded farmer, built end-to-end with real public weather, satellite and price data plus cached fallbacks. Not a production insurance product.

## 2. Problem statement

### Problem

**Pain**
- Small farmers keep records in their heads, a notebook, or scattered WhatsApp photos. They cannot answer basic questions like "what did this crop actually cost me per quintal?" or "did I spend more on fertiliser than last season?"
- Daily risk decisions (spray, irrigate, harvest early) are made without checking the forecast against the crop's current stage.
- After hail, inundation, cloudburst or unseasonal rain at harvest, crop insurance and relief claims fail or get delayed because there is no organised, timestamped record linking the loss to a weather event, and the reporting window for localised calamities is short (about 72 hours under PMFBY; verify against official guidelines).

**Impact**
- Real losses go uncompensated because they cannot be proven in time.
- Input costs drift up season to season without the farmer noticing.
- Generic chatbots cannot help: they have no memory of the farmer's season and cannot produce records they never saw.

**Desired outcome**
- Logging an activity takes under 15 seconds and becomes a confirmed structured record.
- The farmer can ask a plain-language question (Hindi or English) and get an answer computed from their own records, with the source records shown.
- When heavy rain is observed over a plot, the farmer is alerted the same day and can produce an evidence pack in one tap, well inside the reporting window.

**Non-goals**
- Not an insurance product: it never files, submits or decides claims.
- No pesticide dosage recommendations or crop-disease diagnosis.
- No payments, loans, marketplace or selling features.
- No individual drought claims (drought is assessed area-wide, not per farmer).

## 3. Target users and user tasks

### Users and tasks

**Farmer (primary)**: small/medium farmer, Hindi-first, phone-only, low typing comfort. Single user, no login in the MVP.
- Set up plots and the current season (crop, area, sowing date, location pin).
- Log an activity by typing, speaking or taking a photo, then confirm the parsed record.
- View the ledger timeline and costs for each plot and season.
- Ask questions such as "cost per quintal on plot 2 vs last season?" or "can I spray tomorrow?".
- See the risk level for each plot for the next 5 days.
- Respond to a weather alert: confirm or dismiss a suspected loss event and add photos.
- Generate, view and download the evidence pack PDF.

**Helper (secondary)**: a family member or Krishi Mitra-style volunteer using the farmer's phone. Same tasks as the farmer; entries are marked `source` so it is clear how they were logged. No separate permissions in the MVP.

**Demo operator (developer)**: the team member running the live demo.
- Reset the database to seeded demo data with one action.
- Trigger a weather check on demand instead of waiting for the schedule.
- Run the full flow with no LLM API key (deterministic fallback mode) and with cached weather, satellite and price responses if the network fails.

## 4. Core features

### Core features

**Must-have**
1. **F1 Plot and season setup**: create/edit plots (name, area in acres, location pin) and seasons (crop, season label, sowing date). A plot can have many seasons; only one season per plot is `active`.
2. **F2 Quick log (parse + confirm)**: the user types a free-text entry in Hindi, English or mixed; the server parses it into a draft structured entry; the UI shows a confirm card the user can edit; nothing is saved until the user taps Confirm.
3. **F3 Ledger view**: per-plot, per-season timeline of entries grouped by date, with category icons, running total cost, and filters by category.
4. **F4 Season metrics**: deterministic totals per season: total cost, cost by category, harvested quantity, cost per quintal, revenue, profit.
5. **F5 Agent Q&A**: the user asks a question; a bounded agent (max 6 tool calls) answers using only the allowlisted tools in section 6 and shows the source records/data it used.
6. **F6 Spray check**: rule-based "OK / Not advised" verdict for a plot and date using the hourly forecast, with the reason.
7. **F7 Plot risk score**: Low / Medium / High risk for the next 5 days per plot, from forecast + crop stage.
8. **F8 Weather monitor (auto-trigger)**: on a schedule and on demand, checks observed weather for every plot with an active season and opens a `suspected` event when a threshold is crossed; the farmer gets an in-app alert.
9. **F9 Loss event flow**: the farmer confirms or dismisses a suspected event, or reports one manually; confirmed events show a 72-hour reporting countdown.
10. **F10 Satellite crop-health change**: Sentinel-2 NDVI for the plot before vs after an event, plus an NDVI time series for the season, with a cached fallback for demo plots.
11. **F11 Evidence pack PDF**: one tap generates a PDF for a confirmed event: farmer/plot/crop details, ledger timeline, area weather vs normal, satellite before/after, photo timeline, farmer-entered loss estimate, disclaimer.
12. **F12 Demo data and reset**: seeded farmer, plots, seasons and entries; one action resets to the seed.
13. **F13 Health check**: reports server status, configured/observed integration modes, and whether synthetic sample fixtures are enabled.

**Should-have**
14. **F14 Photo log**: upload/capture a photo; store with timestamp and location; optional vision tag (`healthy`, `pest_damage`, `waterlogging`, `lodging`, `unclear`) shown as a hint, never a diagnosis.
15. **F15 Voice input**: speech-to-text in Hindi (hi-IN) and English feeding the F2 parser, with typed fallback.
16. **F16 Mandi price check**: latest modal price for the crop at the nearest configured market, with cached fallback, compared against the season's cost per quintal.
17. **F17 Cost benchmark**: compare the farmer's cost per quintal with the official state average from the Cost of Cultivation dataset.

**Nice-to-have**
- **N1** Nearby fire alert: NASA FIRMS active-fire detections within 1 km of a plot open a `natural_fire` suspected event.
- **N2** WhatsApp-shareable season summary card (image).
- **N3** Second regional language (Telugu or Tamil).
- **N4** Offline-first logging that syncs later.

**Out of scope**: login/accounts, multi-farmer admin, claim submission, contacting insurers or officials, payments, pesticide dosing, disease diagnosis.

## 5. Inputs and data sources

### Inputs and data sources

#### Input channels
- **Quick log text**: 1 to 500 characters, Hindi (Devanagari), English or mixed. Required for `/api/entries/parse`.
- **Voice**: browser speech-to-text produces the same text input; no audio is stored.
- **Photo upload**: JPG/PNG/HEIC, max 8 MB, optional; captured timestamp and GPS from EXIF if present, otherwise upload time and the plot's location (marked `location_source: plot_pin`).
- **Forms**: plot, season, event and loss-estimate forms (fields below).
- **Environment variables**: listed in section 9.

#### Data model
All dates ISO `YYYY-MM-DD`, timestamps ISO 8601 with offset, currency INR (₹) as decimal with 2 places, quantities in the stated unit. Costs are always positive numbers; revenue comes only from `sale` entries.

**Farmer**: `farmer_id` (string, required) · `name` (string 1-80, required) · `language` (enum `hi`, `en`, default `hi`) · `phone` (string, optional) · `state` (string, required, used for benchmarks) · `district` (string, required) · `village` (string, optional)

**Plot**: `plot_id` (string) · `farmer_id` · `name` (string 1-60, required) · `area_acres` (decimal > 0 and ≤ 100, required) · `lat` (decimal −90..90, required) · `lon` (decimal −180..180, required) · `survey_number` (string, optional, khasra/survey no.) · `nearest_market` (string, optional)

**Season**: `season_id` · `plot_id` · `crop` (enum `paddy`, `wheat`, `tomato`, `other`) · `season_label` (string, e.g. "Kharif 2026") · `sowing_date` (date, required) · `status` (enum `active`, `closed`) · `policy_number` (string, optional, farmer-entered insurance application number)

**EvidencePack**: `pack_id` · `event_id` · `generated_at` · `file_path` · `data_sources` (list of `{name, mode: live|cached, fetched_at}`)

**Benchmark**: `crop` · `state` · `year` · `cost_per_quintal_inr` · `source` (string). Loaded from the Directorate of Economics & Statistics Cost of Cultivation dataset (data.gov.in) downloaded as CSV before the event.

**CropCalendar** (config): crop → stage day ranges counted from `sowing_date`:
- paddy: vegetative 0-59, flowering 60-89, maturity 90-119, harvest_ready ≥ 120
- wheat: vegetative 0-59, flowering 60-94, maturity 95-124, harvest_ready ≥ 125
- tomato (from transplanting): vegetative 0-34, flowering 35-59, fruiting 60-99, harvest_ready ≥ 100
- other: stage `unknown`

## 6. Processing rules and business logic

### Processing logic

#### Pipeline
log text → **L1 parse** → confirm card → save Entry → **L2 metrics** on demand → agent/tools → **L6 monitor** → Event → **L8 evidence pack**.

**Core principle:** the LLM never does arithmetic, never invents history, and never decides thresholds. All numbers come from the database or external data via deterministic server code; the LLM only parses text and explains tool results.

#### L1 Log parsing
1. Input text goes to the LLM with a fixed system prompt and must return `ParsedEntry` JSON; validate against the schema, coerce enums, reject unknown fields.
2. Relative dates ("aaj", "kal", "today", "yesterday") are resolved by the server against the server's local date (Asia/Kolkata), not by the LLM. Missing date → today.
3. `plot_hint` is matched to a plot name case-insensitively and by plot number ("plot 2" → second plot by creation order). If no match and the farmer has more than one plot, the confirm card asks the user to choose.
4. Any null required field is listed in `missing_fields` and highlighted on the confirm card. Never guess a cost.
5. **Fallback (no `GEMINI_API_KEY`)**: regex parser that extracts amounts after "₹" or "rs/rupaye", numbers + units (kg, bag, quintal), and category keywords in Hindi and English (e.g. "DAP/urea/khad" → fertiliser, "beej/seed" → seed, "spray/dawa" → pesticide, "majdoor/labour" → labour, "paani/irrigation" → irrigation, "katai/harvest" → harvest, "becha/sold" → sale). Anything unmatched → category `note`.

Example: "Sowed wheat on plot 2, 50 kg DAP, ₹1,400" → `{category: fertiliser, item: "DAP", quantity: 50, unit: kg, cost_inr: 1400.00, plot_hint: "plot 2", entry_date: today}`.

#### L2 Season metrics (deterministic, server)
- `total_cost` = sum of `cost_inr` for non-deleted entries in categories other than `sale` and `harvest`.
- `cost_by_category` = same sum grouped by category.
- `harvest_quintals` = sum of `quantity` for `harvest` entries (convert kg ÷ 100).
- `cost_per_quintal` = `total_cost / harvest_quintals`, rounded to 2 dp; null if no harvest yet.
- `revenue` = sum of `cost_inr` of `sale` entries.
- `profit` = `revenue − total_cost`; if no sales yet, `projected_profit(price)` = `harvest_quintals × price − total_cost`.
- `compare_seasons(plot, crop, metric)`: the active season vs the most recent closed season of the same crop on the same plot; `change_pct = (current − previous) / previous × 100`, 1 dp.
- Rounding: half-up to 2 dp for money, 1 dp for percentages.

#### L3 Spray check (deterministic)
For plot P and date D (default tomorrow), using hourly forecast for 06:00 to 18:00 on D (the spray window) plus the following `SPRAY_RAIN_LOOKAHEAD_HOURS` (default 24):
- **Not advised (rain)** if total precipitation over the window + lookahead ≥ 1.0 mm OR any hour has precipitation probability ≥ 50%.
- **Not advised (wind)** if all spray-window hours have wind speed > 15 km/h.
- **Caution (heat)** if every spray-window hour is > 35 °C; suggest the coolest 3-hour block.
- Otherwise **OK**, with the best 3-hour block (lowest wind, no rain).
- Returns `{verdict, reasons[], best_window, forecast_hours_used}`. Never mentions products or doses.

#### L4 Crop stage
`days = today − sowing_date`; stage from the CropCalendar ranges in section 5. Sensitive stages: `flowering`, `fruiting`, `maturity`, `harvest_ready`.

#### L5 Plot risk score (next 5 days, deterministic)
Per day in the forecast: daily precipitation ≥ 64.5 mm → +3; 15.6 to 64.4 mm → +1; max temperature ≥ 40 °C → +2; max wind gust ≥ 40 km/h → +1; weather code for thunderstorm with hail → +3. `raw_score` = max over the 5 days. If crop stage is sensitive, `score = raw_score × 1.5` rounded down. Level: 0-1 `low`, 2-3 `medium`, ≥ 4 `high`. Returns `{level, score, stage, drivers[] (e.g. "Heavy rain 82 mm forecast on 2026-11-02"), forecast_fetched_at}`. Thresholds come from config, not code literals.

#### L6 Weather monitor (auto-trigger)
- Runs every `MONITOR_INTERVAL_HOURS` (default 6) and on `POST /api/monitor/run`.
- For each plot with an active season, fetch observed daily weather for the last 3 days.
- Trigger rules: observed daily precipitation ≥ `HEAVY_RAIN_MM` (64.5) → suspected event; type `unseasonal_rain_post_harvest` if the stage is `harvest_ready` or a `harvest` entry exists within the last 14 days, else `inundation`. Weather code for hail → type `hail`.
- De-duplicate: do not open a new event if an event (any status except `dismissed`) exists for the same plot within ±2 days of the date.
- Creates Event `{status: suspected, trigger: auto_weather, trigger_detail}` and an in-app alert: "Heavy rain (78.4 mm) recorded near Nahar wala khet on 14 Oct. Was your crop damaged? Confirm and add photos."
- Heatwave readings create a risk alert only, not a loss event.

#### L7 Event state machine
`suspected → confirmed` (farmer taps "Yes, damaged") or `suspected → dismissed`. Manual reports start as `confirmed`. `confirmed` events show a countdown to `report_deadline`; after the deadline the UI shows "Reporting window passed. You can still generate the record, but contact your insurer or agriculture office directly." Only `confirmed` events can generate a pack. `dismissed` is final in the MVP.

#### L8 Satellite NDVI (F10)
- Area of interest: circle around the plot pin with radius `sqrt(area_m² / π)` (2 acres → ~51 m).
- Sentinel-2 L2A, mask clouds/shadows using the scene classification layer; drop images with > 30% of the AOI masked.
- `ndvi_before` = median NDVI of the clearest image in `[event_date − 20, event_date − 1]`; `ndvi_after` = clearest image in `[event_date + 1, event_date + 20]`; `ndvi_change_pct` 1 dp.
- If no valid image in a window: return `null` with note "No cloud-free satellite image in this window".
- If a `harvest` entry falls between the two images, add the note "Harvest occurred between images; NDVI drop may reflect harvesting, not damage." Satellite data is supporting context only.
- Season series: one median NDVI value per valid image from `sowing_date` to today.
- If GEE is unavailable, serve cached values for seeded plots and mark `mode: cached`.

#### L9 Evidence pack (F11)
Built only from stored records and fetched data. Sections in order:
1. Header: "CropTrail loss evidence record", generated timestamp, pack id.
2. Farmer, village/district/state, plot name, survey number, area, pin coordinates, crop, season, sowing date, policy number if entered.
3. Event: type, date, how it was detected (`trigger_detail`), date confirmed, reporting deadline.
4. Ledger timeline for the season (date, category, item, qty, cost) and total cost to date.
5. Area weather evidence: observed daily rainfall and max temperature for `event_date − 3` to `event_date + 2`, alongside the 1991-2020 average daily rainfall for that calendar month, labelled "Area weather (gridded model data, several km resolution), source: Open-Meteo".
6. Satellite crop health: before/after NDVI, change %, image dates, notes from L8.
7. Photo timeline: thumbnails with timestamp, coordinates, `location_source`, vision tag labelled "AI hint, not a diagnosis".
8. Estimated loss: farmer-entered quantity × latest cached mandi modal price, clearly labelled "Farmer's estimate".
9. Data sources list with live/cached mode and fetch time.
10. Disclaimer: "This document is a supporting record prepared by the farmer using CropTrail. Claim eligibility, assessment and settlement are decided only by the official crop insurance scheme and its insurer."

The required claim fields must be copied by the team from the official PMFBY intimation documents into a config list; the LLM never decides them.

#### L10 Agent (F5)
- Tools (allowlist): `query_ledger(plot_id, season_id, category, from, to)`, `get_season_metrics(season_id)`, `compare_seasons(plot_id, crop, metric)`, `get_forecast(plot_id, days≤7)`, `spray_check(plot_id, date)`, `get_plot_risk(plot_id)`, `get_weather_history(plot_id, from, to)`, `get_ndvi(plot_id, from, to)`, `get_mandi_price(crop, market)`, `get_benchmark(crop, state)`, `projected_profit(season_id, price)`, `list_events(plot_id)`, `generate_evidence_pack(event_id)`.
- Loop: max 6 tool calls per question; each tool argument is validated against its schema; invalid arguments return an error to the agent, not a crash. Stop when the LLM returns a final answer or the cap is hit (then answer with what it has and say it stopped).
- `generate_evidence_pack` via the agent requires explicit user confirmation in the UI before running.
- The answer must cite the tool results it used; the response includes `sources[]` the UI renders as chips.
- Answers in the language of the question.
- Refusals: pesticide/fertiliser dosage, disease diagnosis, legal or claim-eligibility questions → "Please check with your local Krishi Vigyan Kendra or agriculture office." Missing data → "I don't have a record of that in your ledger." Never guess.
- **Fallback (no `GEMINI_API_KEY`)**: keyword intent router (Hindi + English) for six intents: fertiliser comparison, cost per quintal, spray check, profit at current price, season summary, prepare claim file. Each maps to a fixed tool sequence and a fixed answer template, e.g. "Fertiliser spend this season: ₹{cur}. Last season: ₹{prev}. Change: {pct}%." Unknown intent → "In demo mode I can answer: ..." listing the six.

#### L11 Mandi price and benchmark
- Price: latest record by date for crop + market; if older than 7 days show "as of {date}". Fallback to cached CSV marked `cached`.
- Benchmark: `difference_pct = (farmer_cpq − benchmark_cpq) / benchmark_cpq × 100`, 1 dp; show "above/below state average". Hidden if benchmark row missing.

#### L12 Photo vision tag (F14)
Optional LLM vision call returns `{vision_tag, vision_confidence}`; if confidence < 0.6 store `unclear`. Never shown as a diagnosis. Without a key, tag is null.

## 8. Error handling and edge cases

### Error handling and edge cases

| # | Case | Response | User sees |
|---|---|---|---|
| E1 | Empty log text | 422 | "Please type or say what you did." |
| E2 | Log text > 500 chars | 422 | "Please keep each log under 500 characters." |
| E3 | Parser cannot extract anything | 200, category `note`, all fields in `missing_fields` | Confirm card with fields to fill in manually |
| E4 | LLM key missing | Fallback parser/agent, `mode: fallback` | "Demo mode" pill; features still work |
| E5 | LLM call fails or times out (20 s) or returns invalid JSON | Retry transient provider/network failures with exponential backoff (up to 3 attempts), then fallback; do not retry permanent client errors | Show a clear basic-answer notice with the provider failure reason |
| E6 | Photo > 8 MB | 413 | "Please use a photo smaller than 8 MB." |
| E7 | Unsupported file type | 415 | "Only JPG, PNG or HEIC photos are supported." |
| E8 | Plot ambiguous or not found in log | 200, `resolved_plot_id: null` | Confirm card asks "Which plot?" with plot buttons |
| E9 | Duplicate entry (same season, date, category, item, cost within 10 min) | 409 with existing `entry_id` | "This looks like a duplicate of an entry you just saved. Save anyway?" |
| E10 | Cost per quintal with no harvest entry | `cost_per_quintal: null` | "Add your harvest quantity to see cost per quintal." |
| E11 | Season comparison with no previous season | Tool returns `previous: null` | "No earlier season of this crop on this plot to compare with." |
| E12 | Weather API unreachable | Use cached response if under 24 h old (`mode: cached`), else 503 | "Weather data unavailable right now. Showing last saved forecast from {time}." or "Weather data unavailable. Try again in a few minutes." |
| E13 | No cloud-free satellite image in a window | NDVI value null with note | "No clear satellite image for this period (clouds)." Pack still generates |
| E14 | GEE credentials missing/failing | Cached values for seeded plots, else null | "Satellite data not available for this plot." |
| E15 | Mandi API key missing or call fails | Cached CSV | Price card with "cached" chip and its date |
| E16 | Generate pack for `suspected` or `dismissed` event | 409 | "Confirm the damage first to create an evidence pack." |
| E17 | Act on an event in the wrong state (e.g. confirm a dismissed event) | 409 | "This alert was already closed." |
| E18 | Event/plot/season id not found | 404 | "We couldn't find that record. It may have been deleted." |
| E19 | Evidence pack after report deadline | 200, pack generated, flag `past_deadline: true` | Warning banner from L7 on the pack screen and in the PDF |
| E20 | Agent hits 6-tool cap | 200, `stopped_at_cap: true` | Best partial answer + "I stopped early. Try asking a simpler question." |
| E21 | Agent asked for dosage/diagnosis/eligibility | 200 refusal | "Please check with your local Krishi Vigyan Kendra or agriculture office." |
| E22 | Server not reachable from client | Client-side | Full-screen card: "Can't connect to CropTrail. Check your internet and try again." with **Retry** |
| E23 | Invalid coordinates or area on plot form | 422 with field errors | Inline red text under each field |
| E24 | Speech recognition unsupported or fails | Client-side | Mic button disabled with tooltip "Voice not available, please type." |
| E25 | Monitor finds an event already open within ±2 days | No new event | Nothing new; logged in monitor response as `skipped_duplicate` |

**Retry policy**: one automatic retry for LLM and external API calls with a 2 s backoff; no automatic retry for write operations (entries, events, packs); never retry a request that returned 4xx.
**Partial success**: the evidence pack always generates with whatever sections have data; missing sections show "Not available" plus the reason, and `data_sources` records which failed.

## 9. Safety, privacy, constraints, and integrations

### Safety, privacy, constraints, integrations

#### Safety rules (never automatic)
- Never submit, file or send a claim, message, email or SMS to an insurer, bank, official or anyone else. The pack is only generated and downloaded by the farmer.
- Never recommend pesticide or fertiliser doses, product names for treatment, or diagnose crop disease. Vision tags are "hints" only.
- Never state claim eligibility, compensation amounts or legal advice.
- `generate_evidence_pack` from the agent requires a user confirmation tap.
- Loss estimates are always the farmer's own input and labelled as such.
- Never fabricate or edit weather, satellite or price values; everything shown carries its source and live/cached mode.

#### Privacy
- Fictional demo data only; no real farmer data in the repo or demo.
- Do not collect Aadhaar, bank account numbers or IFSC codes. The policy number is the only insurance identifier and is optional.
- Data stored locally in a single SQLite database file and a local `uploads/` folder; nothing sent to third parties except: question/log text to the LLM provider and plot coordinates to weather/satellite/price APIs.
- Do not log full raw log text, photos or phone numbers in server logs; log ids only.
- Strip EXIF from stored photo copies after reading timestamp and GPS into the database.

#### Security
- All API keys only in server environment variables; never in client code or the repo.
- CORS limited to `CLIENT_ORIGIN`.
- Input limits: log text 500 chars, notes 500 chars, photo 8 MB, agent question 300 chars.
- Prompt injection: treat all farmer text, ledger contents and API data as data, never instructions; the agent can only call allowlisted tools with schema-validated arguments; tool outputs never change the system prompt.
- Local mode has no authentication; hosted demo mode uses single-password access control, as documented in the README.

#### Technology (team's chosen stack)
- Client: Next.js (React) + Tailwind CSS, mobile-first.
- Server: Python FastAPI (chosen because the Earth Engine and PDF tooling are Python).
- Database: SQLite.
- PDF: a server-side Python PDF library; charts rendered server-side as images.
- LLM: any provider with JSON output and tool calling, accessed only through the AI service module; model name via env var.
- Speech: browser Web Speech API (hi-IN, en-IN).
- Scheduler: in-process background job in the server for the weather monitor.
- Tests: pytest for server; client production build must succeed.

#### Project structure
- `client/`: pages (home, log, ledger, ask, alerts), components, API client, i18n strings (`hi`, `en`).
- `server/api/`: route handlers.
- `server/models/`: data models and schemas.
- `server/tools/`: deterministic logic (metrics, spray check, risk, crop stage, monitor, NDVI, evidence pack builder, price, benchmark).
- `server/services/`: external clients (weather, satellite, mandi, firms) each with a cache layer.
- `server/ai/`: the only module allowed to call the LLM (parser, agent loop, vision tag) plus fallbacks.
- `server/config/`: thresholds, crop calendar, claim field list, intent keywords.
- `server/seed/`: seed data and cached fixtures (JSON/CSV).
- `server/tests/`.

#### Integrations
Open-Meteo (forecast + archive), Google Earth Engine (Sentinel-2 L2A), and data.gov.in Agmarknet are wired. Live responses are cached by request; fictional fixtures are available only when both `USE_CACHED_DATA=true` and `ALLOW_SAMPLE_FIXTURES=true`. Health reports `configured` until an integration request has run; it does not probe third-party services. No live benchmark source or NASA FIRMS integration is configured.

#### Hosted demo
Render Blueprint configuration is in `render.yaml`. The client and server use free services, so they can sleep when idle and server SQLite data and uploads are ephemeral and can be lost on restart or deploy. Production mode refuses to start without `APP_PASSWORD` (at least 16 characters) and `SESSION_SECRET` (at least 32 characters). All `/api` endpoints except health, login and session status require an HTTP-only, secure, SameSite-strict signed session cookie. This is single-password access control for a disposable demo, not multi-user authorization.

- Built in 48 hours by a small team: must-haves first; cut order if late: N1-N4, F17, F16, F15, F14.

- External API usage stays within free tiers.
- Runs locally with one command per part (client, server).
